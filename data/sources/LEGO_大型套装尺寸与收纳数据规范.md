# LEGO 大型套装尺寸与收纳数据规范

版本：1.1  
状态：生效  
制定日期：2026-07-19  
适用数据集：大型套装 Top 100、Top 500 及后续同口径扩展

> 核心原则：成品尺寸、包装尺寸、Brickset 原始值和订正值必须分开保存。订正值可以帮助选柜和规划空间，但不能冒充官方数据，也不能覆盖原始数据。

## 1. 文档目的

本规范统一记录 LEGO 大型套装尺寸与收纳研究中的榜单口径、数据来源、字段含义、证据分类、计算方法、异常处理、更新流程和质量检查。目标是让任何一条尺寸都能回答以下问题：

- 它描述成品还是包装？
- 它来自 LEGO 官网、Brickset API，还是本地计算？
- 三个数是否能确认高、宽、深？
- 它能否用于判断占地、展示罩、包络体积或仓储空间？
- 如果原始数据不完整，订正值是直接恢复的，还是估算的？
- 若数据缺失或冲突，应如何处理？

## 2. 适用范围与榜单口径

### 2.1 大型套装候选

当前榜单从 Brickset API v3 的 `getSets` 结果中筛选：

1. `category = Normal`；
2. `released = true`；
3. 名称已经公开，排除空名称和 `{?}` 占位名称；
4. `pieces` 为有效整数；
5. 按 `PiecesDESC` 排序后取前 N 名。

`released=true` 表示 Brickset 已将记录标记为正式公开记录，不保证当前日期已经开售；实际上市时间以 `launchDate` 为准。

### 2.2 Top 100 与 Top 500

- Top 100：用于重点人工核验、官方轴向补充和展示柜优先级判断。
- Top 500：用于更广泛的尺寸、包装、重量和收纳分析。
- Top 500 的前 100 条必须与同一快照下的 Top 100 完全一致。

### 2.3 “大型”与“常见”的边界

主排名依据是零件数，不是拥有量、价格或物理体积。因此：

- Art、马赛克和教育套装可能因为小颗粒很多而排名靠前，但并不一定占用很大空间。
- `owned` 和 `wanted` 只作为流行度参考，不参与当前排名。
- 若未来要生成“常见大型套装榜”，应另行定义拥有量门槛或复合评分，不得悄悄改变本榜单口径。

## 3. 数据源与优先级

### 3.1 LEGO 官方产品页或官方新闻页

用途：确认成品的高、宽、深以及对应展示姿态，是模型轴向数据的最高优先级来源。

只有页面明确使用 high/tall、wide、deep/long 等轴向描述，并能确认尺寸对应完整模型或明确配置时，才可写入“官方 H×W×D”。官方页面只给一边或两边时，不补猜缺失轴。

### 3.2 Brickset API v3

当前结构化数据的主要来源。使用字段包括：

- `setID`、`number`、`numberVariant`、`name`、`year`、`theme`；
- `pieces`、`released`、`launchDate`、`lastUpdated`；
- `collections.ownedBy`、`collections.wantedBy`；
- `modelDimensions.dimension1/2/3`；
- `dimensions.height/width/depth/weight`；
- `extendedData.description`，用于从产品描述中找回尺寸方向或完整数字；
- `bricksetURL`。

原始 API 响应必须作为快照保存，标准化数据不得覆盖或删除原始字段。

### 3.3 Brickset 公共页面

用途：人工交叉核验榜单、名称、零件数和页面展示，不作为当前批量结构化数据的首选来源。网页 HTML 结构可能变化，解析器不能假定零件数字段始终包裹在同一种标签中。

### 3.4 jbryer/brickset 静态数据集

用途：历史分析和 API 不可用时的包装字段回退。2026.0.0 版本覆盖 1970–2025 年，不含 2026 年新增记录，也没有完整导出最新 `modelDimensions`。当前 Top 500 应优先采用实时 Brickset API；静态快照不得覆盖更新的 API 值。

### 3.5 本地人工规则

本地 `dimension_rules.py` 保存：

- LEGO 官方轴向尺寸覆盖；
- 展示姿态、支架、展开/闭合等配置说明；
- 多模型组合例外；
- 每条官方记录对应的来源 URL。

### 3.6 本地订正规则

本地 `dimension_corrections.py` 用来补充非 A 级套装的可用高、宽、深。它主要做三件事：

1. 从产品描述中找回高、宽、深的对应关系；
2. 修复明显被截断或已经过时的 API 数字；
3. 当公开资料不完整时，按照套装结构和最常见的展示姿态给出估算值。

订正结果单独写入 `corrected_*` 字段。Brickset API 原序、官方字段和证据等级都保持原样。

## 4. 核心字段数据字典

|报告列|内部字段/来源|含义与处理|单位|
|---|---|---|---|
|官方 H×W×D|`verified_height_cm`、`verified_width_cm`、`verified_depth_cm`|LEGO 官方明确轴向，经人工核验；不得由 API 原序自动填充|cm|
|API 原序|`modelDimensions.dimension1/2/3`|Brickset 按 LEGO 描述中出现顺序保存的三个模型尺寸；轴向未知|cm|
|订正 H×W×D|`corrected_height_cm`、`corrected_width_cm`、`corrected_depth_cm`|从产品描述恢复，或根据最可能的展示状态补齐；必须同时注明方法和置信度|cm|
|短×中×长|`model_small_cm`、`model_medium_cm`、`model_large_cm`|对当前最可靠的完整模型三边升序排列|cm|
|最长边|`model_large_cm`|当前最可靠三边中的最大值|cm|
|包装 H×W×D|`dimensions.height/width/depth`|未拆封商品包装箱三边，不是成品尺寸|cm|
|包装重量|`dimensions.weight`|整盒商品重量，不是拼装成品净重|kg|
|模型包络体积|三边乘积 ÷ 1000|模型外接长方体体积，不是实体材料体积|L|
|包装体积|包装三边乘积 ÷ 1000|包装箱外接长方体体积|L|
|建议展示罩内尺寸|短、中、长各加 5|选柜起始值；约等于每个方向两侧各留 2.5 cm|cm|

### 4.1 官方 H×W×D

- H = Height，高。
- W = Width，宽。
- D = Depth 或作为陈列纵深使用的 Length，深/长。
- 必须记录尺寸对应的姿态，例如含展示支架、工作姿态、建筑闭合或多个模块叠放。
- 未人工核验时显示 `—`，不得把 API 原序复制过来冒充官方轴向。

### 4.2 API 原序

Brickset 从 LEGO 产品描述中自动提取尺寸，只在描述中恰好找到三个尺寸时保存，并按原文出现顺序写入 `dimension1/2/3`。三个数可能是高、宽、长的任意排列，也可能误碰到多模型描述。

因此 API 原序只能称为 A/B/C 三边，不能直接标注为 H/W/D。

### 4.3 短×中×长与最长边

- A 级记录：对 LEGO 官方 H/W/D 排序。
- B 级记录：对 Brickset API 原序三边排序。
- A-partial、A-multi 和 missing：不构造虚假的完整三边。
- 排序会丢失轴向，只用于容纳性、最长边和包络体积分析。

### 4.4 包装尺寸与重量

- 包装列来自 API `dimensions`，与 `modelDimensions` 完全分离。
- 三个包装尺寸必须全部存在且大于零，才能计算包装体积并标记包装证据为 B。
- 重量缺失显示 `—`，不得按零件数估算后写入原始重量列。
- 包装尺寸不得代替成品尺寸，成品尺寸也不得代替包装尺寸。

### 4.5 订正 H×W×D

“订正 H×W×D”是为了让非 A 级套装也尽量有一组可用于摆放和收纳的方向尺寸。

- H 是高，W 是正面宽度，D 是前后纵深或模型长度。
- 有清楚产品描述时，直接按描述抄写并调整到 H/W/D 顺序。
- API 数字如果明显少了前面的数字，例如 `2.5` 实际应为 `22.5`，订正列使用产品描述中的完整数字，API 原序仍保留错误值，方便追查。
- 只有一边或两边有公开数据时，可以根据对称结构、标准底板或正常展示姿态补齐其他边。
- 完全没有尺寸时，可以按同类套装比例和图片中的正常展示姿态估算，但必须标成低置信度。
- 散件箱、教育活动包、挑战套件和多个独立模型没有一个真实的统一成品尺寸，写“不适用”，不强行编造三边。

Top 500 报告把方法和置信度写在同一个单元格里，例如：

- `39×75×50〔直录·高〕`：数字和方向都能从产品描述中找到；
- `41×51×51〔推定·高〕`：已有两边，第三边可由对称结构可靠补齐；
- `14×31×124.5〔估计·低〕`：只有部分公开尺寸，其余按模型形态估算；
- `不适用（多个独立模型）`：这套产品没有一个合理的统一 H/W/D。

## 5. 模型尺寸证据分类

证据代码是本项目的来源分类，不是 Brickset 官方评级，也不是统计置信度。A-partial 和 A-multi 是特殊状态，不能简单理解为介于 A 与 B 之间。

这里的证据等级只说明原始数据来自哪里、能安全用到什么程度。它与订正列的“高/中/低置信度”是两套不同标记。例如，一条记录可以仍然是 B 级，但订正列通过产品描述找回了清楚的 H/W/D，因此订正置信度可以是高。

|代码|判定条件|允许使用|禁止使用|
|---|---|---|---|
|A|LEGO 官方明确完整 H/W/D，姿态已确认|轴向判断、占地、排序、最长边、包络体积、展示罩起始值|忽略配置说明直接套用于其他姿态|
|A-partial|LEGO 官方只给一边或两边|已知边和最长已知边的提示|完整体积、完整展示罩、缺失轴猜测|
|A-multi|官方数字属于多个独立模型，不能组成单一包络|逐模型说明|把多个模型高度相乘或当作一个 H/W/D|
|B|API 三个模型尺寸都存在且大于零，但轴向未知|短×中×长、最长边、包络体积、全向容纳参考|标注 H/W/D、直接判断桌面宽度与纵深|
|missing|没有完整 API 三边，也没有可靠官方覆盖|展示缺失状态、进入待核验队列|任何成品空间计算|

### 5.1 包装证据

- `package_evidence = B`：API 包装高、宽、深全部存在且大于零。
- `package_evidence = missing`：包装三边不完整或包含无效值。
- 包装重量只记录“有值/缺失”，当前不另设证据等级。

### 5.2 订正方法

|方法|平实解释|通常怎么用|
|---|---|---|
|官方|A 级已经有完整官方 H/W/D，订正列原样带过去|可以直接用于摆放规划，但仍要注意姿态说明|
|直录|产品描述明确写了高、宽、深/长，按文字重新排好顺序|通常可以直接使用|
|推定|至少有一部分可靠尺寸，再用对称结构、标准底板或明确姿态补齐|适合初步选柜，建议留余量|
|估计|缺少完整公开资料，按套装类型、比例和最常见展示状态估算|只适合粗略规划，购买定制柜前应复测|
|不适用|产品是散件、多个独立模型或没有固定成品|不提供统一三边，应按实际摆法单独计算|

### 5.3 订正置信度

- 高：三个方向能从产品描述直接确认，或缺失边可以由非常明确的结构关系补齐。
- 中：部分尺寸可靠，其他尺寸需要做有限推断。
- 低：主要根据套装类型、图片比例或同类模型估算，误差可能较大。
- 官方：沿用 A 级官方尺寸，不再重复标高/中/低。

置信度只评价订正值，不会改变 `model_evidence`。

## 6. 计算规则

### 6.1 数值有效性

- 只接受有限、可解析且大于零的数值。
- 零、负数、空值、无法解析的文本均视为缺失。
- 不因其他两边存在而补猜第三边。

### 6.2 模型三边选择

1. 若存在 A 级官方完整 H/W/D，使用官方三边生成短、中、长及派生值。
2. 否则，若 API 三边完整有效，使用 API 原序三边生成短、中、长及派生值，证据为 B。
3. A-partial 只保留官方已知边；A-multi 清空统一包络；missing 不计算。

以上规则用于原始尺寸、短×中×长、最长边和原始包络体积。订正尺寸是另一层数据，不反过来填充这些原始字段。这样可以清楚看出哪些是原始数据，哪些是后来补的。

### 6.3 公式

模型包络体积：

`model_envelope_volume_l = dim1 × dim2 × dim3 ÷ 1000`

包装体积：

`package_volume_l = package_height × package_width × package_depth ÷ 1000`

展示罩起始尺寸：

`display_case_dims = sorted_model_dims + 5 cm/边`

### 6.4 精度与显示

- API 原始尺寸保留 API 数值。
- 报告中的普通尺寸通常显示 1 位小数；官方整数按官网值显示。
- 包络体积保留 2 位小数。
- 包装重量保留最多 3 位小数。
- 排序、最大值和体积使用未格式化数值计算，不能用显示字符串反算。

## 7. 特殊情况处理

### 7.1 多模型组合

例如 72153 的三个数字分别是妙蛙花、喷火龙和水箭龟各自的高度，并非一个模型的三条轴。该记录标记 A-multi，清空统一短×中×长、最长边、体积和展示罩。

订正列也写“不适用”，除非以后明确规定一套固定摆法，并单独测量这套摆法的整体包络。

### 7.2 可动或多姿态模型

例如 42082 起重机工作姿态与行驶姿态包络不同。官方覆盖必须注明采用的姿态；报告中的派生值只对该姿态有效。

### 7.3 展开与闭合建筑

例如 75827 消防局闭合和展开宽度不同。主记录采用明确标注的基准姿态，其他姿态写入配置备注。

### 7.4 壁挂作品与二维数据

例如 31203 世界地图只有官方高和宽。原始证据仍标记 A-partial，也不计算原始包络体积。订正列可以给出估算厚度，但要标成“推定”，不能写进官方深度字段。

### 7.5 帆、天线、吊臂与柔性件

尺寸应尽量采用正常展示姿态，并在备注中说明是否包含帆、天线、吊臂、织物或展示支架。选柜时应额外检查柔性件和可动范围，不能只依赖理论包络。

## 8. 数据处理与更新流程

1. API Key 仅从进程环境变量 `BRICKSET_API_KEY` 读取，不写入代码、日志、快照或报告。
2. 调用 `checkKey` 验证密钥。
3. 使用 `getSets`、`PiecesDESC`、`pageSize=500` 分页取得候选。
4. 应用本规范第 2 节的筛选条件。
5. 当第 N 名零件数严格大于最后一个 API 候选的零件数时，排名边界得到证明；否则继续请求下一页。
6. 保存原始 API Top N 快照。
7. 标准化模型、包装、重量、来源与更新时间字段。
8. 应用 LEGO 官方覆盖和特殊例外。
9. 应用订正规则，生成 `corrected_*`、订正方法、置信度和说明。
10. 生成报告并执行质量检查。

当前数据规模下：Top 100 通常需要 1 次 `getSets`；Top 500 通常需要 2 次。实际页数应以边界证明为准，不得写死为永久规则。

## 9. 来源优先级与冲突规则

1. LEGO 官方明确轴向优先于 Brickset 模型原序，用于 H/W/D 和派生值。
2. Brickset API 原序仍须保留，不能因官方覆盖而删除，以便审计差异。
3. 当前 API 包装字段优先于年度静态快照。
4. 包装和模型是不同实体，二者不得相互覆盖。
5. 若 LEGO 官方不同页面或不同配置给出不同尺寸，必须记录页面、地区、配置和核验日期，不应无说明地选择较大或较小值。
6. 发现明显多模型误提取、零值或单位异常时，原始字段保持不变并标记问题。可以在订正列中修复，但必须说明方法和置信度。
7. 订正值不能覆盖官方字段、API 原序、短×中×长或原始证据等级。

## 10. 质量检查

每次生成 Top N 数据后必须检查：

- 记录数恰好为 N；
- 排名连续为 1…N；
- 零件数非升序排列；
- `set_id` 唯一；
- 不含空名称或 `{?}` 占位名称；
- 所有记录满足 `category=Normal`、`released=true` 和零件数有效；
- Top 500 的前 100 条与同快照 Top 100 一致；
- 排名边界已经由候选窗口末尾零件数证明；
- 完整包装三边均大于零；
- A 级记录都具有官方来源 URL 和配置说明；
- A-multi 不存在统一体积或展示罩派生值；
- 每条记录都有 `correction_method`；有订正三边时，三个数都必须大于零；
- `not_applicable` 记录的订正三边必须全部为空，并写明为什么不适用；
- 订正为 `direct`、`inferred` 或 `estimated` 时，必须同时保存置信度和简短说明；
- A 级记录的订正三边必须与官方 H/W/D 完全一致；
- JSON 中的订正值必须与 Top 500 完整表逐条一致；
- API Key 未出现在任何输出文件中；
- 原始快照、标准化 JSON 和报告的套装号、排名与零件数一致。

## 11. 可追溯字段

标准化 JSON 应至少保留：

- `set_id` 与 `brickset_set_id`；
- `brickset_url`；
- `model_source_url`；
- `package_source_url`；
- `model_evidence` 与 `package_evidence`；
- `verified_configuration`；
- `retrieved_at`；
- `brickset_last_updated`；
- API 原序三边与官方 H/W/D；
- `corrected_height_cm`、`corrected_width_cm`、`corrected_depth_cm`；
- `correction_method`、`correction_confidence`、`correction_note`；
- 所有派生字段。

报告中的套装号链接：A/A-partial/A-multi 指向对应 LEGO 官方来源；B/missing 指向 Brickset 套装页。

## 13. 已知限制

- Brickset 模型尺寸主要从 LEGO 描述自动提取，轴向未知，老套装覆盖率较低。
- LEGO 官方描述也可能只给部分尺寸、多个组件尺寸或不同姿态尺寸。
- 包络体积是外接长方体，不等于实际模型体积、材料体积或最优摆放体积。
- “短×中×长”不能保证最短边就是高度，也不能保证另外两边就是桌面占地。
- 建议展示罩每边加 5 cm 只是起始值；通风、防尘、底座、灯光、开门和维护空间需要另行考虑。
- 零件数榜单不能替代按拥有量、价格、主题或真实体积定义的榜单。
- 数据会随 Brickset 更新、官方页面变化和人工核验增加而改变。
- 订正值不是测量值。特别是“估计·低”，实际尺寸可能因为姿态、展开方式、支架或柔性零件而明显不同。
- 订正值适合初步规划。若要购买定制展示柜，最好先找实物测量，并在三边都留出余量。

## 14. 变更管理

新增或修改官方覆盖时，应同时记录：

1. 套装号；
2. 官方 URL；
3. H/W/D 或已知部分轴；
4. 使用的展示姿态；
5. 是否包含支架、帆、天线、吊臂或展开结构；
6. 核验日期；
7. 证据等级变更原因。

修改筛选口径、证据定义、公式或缺失值规则时，必须提升本规范版本，并重新生成受影响的数据集和报告。

修改订正值时，还应记录修改原因，例如发现了新的产品描述、修复了 API 截断、改变了默认展示姿态，或者用实物测量替换了估算值。修改后必须同时更新 `large_top500_data.json` 和 Top 500 Markdown 报告。

## 附录 A：术语

|术语|定义|
|---|---|
|成品尺寸|套装按指定姿态拼装完成后的外部尺寸|
|包装尺寸|未拆封商品包装箱的外部尺寸|
|轴向|高、宽、深/长所对应的方向|

|展示罩起始值|在模型短、中、长三边上各增加 5 cm 得到的选柜参考值|
|证据等级|本项目定义的数据来源与可用性分类|
|订正尺寸|为摆放和收纳补充的一组 H/W/D，不覆盖原始数据|
|订正方法|官方、直录、推定、估计或不适用|
|订正置信度|对订正值可靠程度的高、中、低判断，与证据等级分开|
